# Функциональная спецификация платформы

## 1. Назначение платформы

IncidentHub — мультитенантная SOC-платформа класса case management (аналог TheHive-подхода) для работы с:

- алертами от внешних источников;
- расследованиями (cases);
- задачами, observables, таймлайном, страницами и вложениями;
- форум-дискуссиями по кейсам;
- Telegram-коммуникациями в рамках кейса;
- AI-ассистентом для поиска и анализа;
- системными метриками, аудитом и администрированием.

## 2. Пользовательские роли

Платформа реализует следующие уровни доступа:

- `platform_admin`: глобальное администрирование системы и тенантов;
- `tenant_admin`: администрирование внутри конкретного тенанта;
- `analyst`: операционная работа SOC (alerts/cases/tasks/forum/AI);
- `viewer`: ограниченный просмотр (на API-уровне есть проверки роли, чувствительные операции запрещены).

## 3. Мультитенантность

Бизнес-изоляция реализована tenant-scoped моделью:

- у каждой сущности бизнес-уровня есть `tenant_id`;
- все tenant-операции проходят через `X-Tenant-ID`;
- middleware разрешает доступ к тенанту только при активном membership;
- часть справочников поддерживает global + tenant override через `catalog_items`.

## 4. Основные функциональные блоки

### 4.1 Alerts

Возможности:

- просмотр списка алертов тенанта;
- карточка алерта (`/alerts/:id`);
- создание/обновление;
- массовый выбор и привязка к существующему кейсу;
- создание нового кейса из набора алертов;
- хранение связи `alerts.case_id`.

### 4.2 Cases

Возможности:

- создание кейса с расширенными полями (source, incident type, priority, confidence, timeline dates и т.д.);
- редактирование статуса, серьезности, владельца и описания;
- пользовательские tenant-статусы кейсов;
- объединение с форумом (1 кейс -> 1 форум-тред);
- получение AI-анализа кейса с сохранением истории перезапусков.

### 4.3 Case workspace

Для кейса доступны разделы:

- задачи (`tasks`);
- observables (`case_observables`);
- timeline events (`case_timeline_events`);
- pages (`case_pages`);
- attachments (`case_attachments` + S3);
- comments (`catalog_items` kind `case_comments`);
- AI verdict/history (`case_ai_analyses` и `catalog_items` kind `case_meta`).

### 4.4 Forum

Возможности:

- список тредов;
- создание треда для кейса (ограничение уникальности в БД);
- публикация сообщений;
- отправка сообщения во внешний канал через Telegram connector;
- синхронизация ответов обратно в форум.

### 4.5 Case communications (Telegram)

Платформа поддерживает tenant-scoped Telegram connector слой только для коммуникаций:

- создание communication thread внутри кейса;
- отправка сообщений в Telegram из кейса;
- синхронизация входящих ответов обратно в thread;
- хранение сообщений/метаданных в tenant-изолированном catalog.

### 4.6 AI

Два ключевых сценария:

- AI чат по данным текущего тенанта (persisted session history);
- AI-анализ конкретного кейса с сохранением всех запусков.

Источник знаний AI:

- retrieval из Elasticsearch по тенант-данным;
- генерация ответа через Ollama-модель.

### 4.7 Администрирование

Доступно admin-пользователям:

- тенанты (создание, изменение, ответственный пользователь);
- пользователи и роли;
- API tokens, rate limits, achievements;
- achievement icons: выбор из минималистичного пакета (`/achievement-icons/*.svg`) + загрузка собственной иконки в S3 (PNG/JPEG/SVG, до 2MB, 64-512px, квадрат);
- настройка tenant-scoped Telegram-ботов для доставки уведомлений;
- системный ресурсный дашборд;
- workflow studio (`workflows` + run history).

## 5. Сквозные бизнес-процессы

### 5.1 Alert -> Case

1. Alerts создаются через API (sync/async).
2. Аналитик привязывает алерты к кейсу или создает кейс из выбранных алертов.
3. Кейс ведется через workspace до резолюции.

### 5.2 Case discussion -> External channel

1. В кейсе создается forum thread.
2. Сообщение публикуется локально.
3. При выборе outbound connector сообщение отправляется наружу.
4. Ответ внешнего сервиса сохраняется как post в тот же thread.
5. Дополнительно можно запускать sync для догрузки сообщений.

### 5.3 AI workflow

1. Пользователь задает вопрос через AI panel.
2. Backend делает поиск по Elasticsearch в рамках tenant.
3. Формирует контекст и обращается к LLM (Ollama).
4. Возвращает ответ + рекомендации + источники.
5. Вопрос/ответ сохраняются в `ai_chat_messages`.

## 6. Нефункциональные требования (реализация)

- горизонтально масштабируемый stateless backend (сессии/данные не в памяти процесса);
- PostgreSQL как source of truth;
- Redis для rate-limit и API cache;
- Elasticsearch для поиска и AI retrieval;
- S3-совместимое хранение артефактов;
- метрики Prometheus + системные health endpoints;
- health checks модулей в API с таймаутом 5 секунд.
