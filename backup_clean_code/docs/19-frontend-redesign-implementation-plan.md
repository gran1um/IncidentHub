# IncidentHub: план глобальной переработки frontend под Figma

Дата: 2026-03-01  
Figma: [IncidentHub](https://www.figma.com/design/ufZSszGUkcF6HV56CZW6L0/IncidentHub?node-id=0-1&p=f&t=mHMHRjZHJI9UGJ0g-0)

## 1) Цель

Сделать полный редизайн frontend с точным соответствием макету Figma, без iframe и без временных “заглушечных” решений, с последующей актуализацией backend-контрактов под новый UI.

## 2) Результат по завершению

- Полное визуальное соответствие экранов Figma (desktop + mobile).
- Единая дизайн-система в коде (токены, компоненты, состояния).
- Все пользовательские сценарии работают на реальных API.
- Backend-контракты приведены в соответствие с новыми требованиями экранов.
- Обновлены тесты и документация.

## 3) Что уже проанализировано в макете

- Проверен доступ к файлу Figma.
- Снята структура корневого узла (`0:1`) и пример детального экрана `Alert detail` (`7:72`).
- Подтверждена целевая визуальная парадигма:
  - темный интерфейс,
  - фиксированный sidebar + topbar,
  - карточная сетка с плотной иерархией,
  - яркие action-акценты,
  - компактная типографика с выраженными заголовками.

## 4) Нефункциональные ограничения

- **Никаких iframe** в реализации.
- Весь UI-код нативно в текущем frontend (`React + TS`).
- Миграция поэкранно, с сохранением работоспособности на каждом шаге.
- Для каждого завершенного экрана: UI + API + тесты + документация в одном пакете.

## 5) Стратегия реализации

## 5.1 Базовый слой (foundation-first)

1. Ввести/актуализировать дизайн-токены:
   - цветовая палитра,
   - typography,
   - радиусы, тени, бордеры,
   - размеры/ритм отступов.
2. Пересобрать базовые UI-компоненты:
   - `Button`, `Input`, `Select`, `Tabs`, `Card`, `Badge`, `Dialog`, `Tooltip`, `Table`, `Pagination`.
3. Пересобрать глобальный shell:
   - sidebar/topbar/status/global search/notification/AI FAB.

## 5.2 Поэкранная миграция (feature slices)

Для каждого экрана:
1. Снимаем контекст из Figma (`get_design_context`) по конкретному узлу.
2. Перерабатываем страницу и связанные локальные компоненты.
3. Фиксируем API-gap (если UI требует новые поля/ручки).
4. Дорабатываем backend-контракт.
5. Добавляем тесты и обновляем документацию.

## 5.3 Backend alignment

- Контракт-first: UI schema -> API DTO -> handler/service/repo.
- Если макет требует новых блоков/данных:
  - расширяем response-модели,
  - добавляем endpoint или параметризацию существующих,
  - сохраняем tenant isolation и RBAC.

## 7) DoD для каждого экрана

Экран считается завершенным только если:

1. Визуально соответствует Figma (структура, размеры, отступы, состояния, hover/focus/active).
2. Работают все действия пользователя (не только UI, но и реальные API-эффекты).
3. Пройдены:
   - unit тесты страницы/компонентов,
   - интеграционные тесты API-контракта (если контракт менялся),
   - e2e smoke сценарий экрана.
4. Обновлена документация по экрану/контракту.

## 8) Риски и контроль

### Основные риски

- Расхождение макета и текущих backend-данных.
- Накопление “half-migrated” стилей.
- Регрессии в tenant/RBAC сценариях.

### Контроль

- Вести миграцию только по этапам выше, без параллельной хаотичной правки.
- На каждый экран делать отдельный атомарный change-set.
- После каждого этапа — smoke e2e по критическим сценариям.

## 9) Первый рабочий спринт (конкретный старт)

1. Этап A1-A3: токены + базовые компоненты + shell.
2. Этап B1: Dashboard.
3. Этап B2-B3: Activity + Alerts list.

Такой порядок минимизирует повторную переделку: сначала общий каркас/компоненты, потом страницы.
