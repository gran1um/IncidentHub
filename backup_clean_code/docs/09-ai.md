# AI подсистема: чат, retrieval, анализ кейсов

## 1. Архитектура

Компоненты:

- `ai.Service` (`/backend/internal/ai/service.go`)
- Retriever: Elasticsearch client
- LLM provider: Ollama или OpenAI-compatible (`provider_ollama.go`, `provider_openai.go`)
- Persistence: PostgreSQL (`ai_chat_sessions`, `ai_chat_messages`, `case_ai_analyses`)

## 2. Режимы работы

### 2.1 Ask AI (чат)

API:

- `POST /api/v1/ai/ask`
- `GET /api/v1/ai/sessions`
- `POST /api/v1/ai/sessions`
- `PATCH /api/v1/ai/sessions/reorder`
- `DELETE /api/v1/ai/sessions/:sessionID`
- `GET /api/v1/ai/session`
- `GET /api/v1/ai/messages`

Процесс:

1. Выбор/создание chat session пользователя (без принудительного default-чата в списке).
2. Retrieval по tenant данным в Elasticsearch + tenant operational context из PostgreSQL.
3. Автоматический route-профиль (Identity/Network/Persistence/IOC/Case/Alert/General) на основе вопроса и найденных source kinds.
4. Формирование autonomous prompt (system + history + context + JSON output instructions).
   - `POST /api/v1/ai/ask` принимает `language` (`ru`/`en`), но язык пользовательского текста имеет более высокий приоритет:
     - если вопрос на русском, ответ возвращается на русском;
     - если вопрос на английском, ответ возвращается на английском;
     - для системных запросов (например case analysis) используется язык интерфейса, переданный во входном payload.
5. Ответ от LLM:
   - при structured JSON ответе применяется парсинг и нормализация (summary, findings, confidence, next steps);
   - для простых conversational-запросов используется облегченный prompt без JSON-схемы;
   - при plain text ответ возвращается как есть;
   - для операционных запросов типа "сколько кейсов в работе" используется прямой deterministic ответ из tenant context;
   - при timeout/ошибке модели или низкокачественном structured output возвращается явная ошибка fallback (`sec-fallback-error`);
   - служебные `<think>...</think>` блоки и markdown-обертки вырезаются до парсинга/рендеринга ответа;
   - 502 возвращается только для hard misconfiguration (например, AI включен, но LLM client не сконфигурирован).
6. Сохранение Q/A в историю.

### 2.2 Case analysis

API:

- `POST /api/v1/cases/:caseID/ai/analyze`
- `GET /api/v1/cases/:caseID/ai/analyses`

Процесс:

1. Сбор данных кейса (case + tasks + observables + events + pages + comments).
2. Retrieval связанных данных из Elastic.
3. LLM-анализ evidence-first в autonomous стиле.
4. Парсинг JSON-контракта с backward-совместимостью:
   - legacy: `verdict/confidence/summary/recommendations/findings`;
   - autonomous: `classification/confidence_level/assessment/next_steps/findings[]`.
5. Persist результата в `case_ai_analyses`.
6. Обновление последнего verdict в `case_meta`.

### 2.3 AI Agent Queue (autonomous case/alert dispatch)

С 2026-03-04 добавлен автоматический pipeline:

1. создание `case`/`alert` -> enqueue в `ai_agent_queue_events`;
2. background worker берет `queued` события;
3. матчинг `catalog(kind=ai_agents)` по `target_types`, `case_tags`, `alert_sources`;
4. выполнение stage-плана (`investigation_plan`) с enrichment-коннекторами;
5. сохранение run в `catalog(kind=ai_agent_runs)`;
6. опционально: теги в `case_meta`, auto-close по verdict, notify через outbound connectors.

Детальная спецификация и тест-матрица:

- `./docs/20-ai-agent-queue-investigation.md`

## 3. Autonomous SOC подход

Реализация вдохновлена подходом `autonomous-soc-analyst`:

- строгий evidence-first стиль;
- профильные prompt-режимы под тип задачи;
- structured JSON как целевой контракт для модели;
- map findings к MITRE ATT&CK и выделение IOC/next steps.

Технически это реализовано в:

- `/backend/internal/ai/autonomous_soc_agent.go`
- `/backend/internal/ai/service.go`

Поддерживаются два формата structured chat output:

1. object schema (`executive_summary`, `confidence`, `recommended_action`, `findings[]`, `next_steps[]`)
2. array schema (`findings[]`)

## 4. Tenant isolation

AI всегда работает в tenant scope:

- query отправляется с tenant id;
- retrieval-фильтрация по `tenant_id`;
- chat sessions/messages и case analyses имеют `tenant_id`.
- tenant operational context из PostgreSQL собирается через read-only MCP-инструменты с allowlist (`AI_MCP_*`), без прямых cross-tenant запросов.

## 5. История и контекст

- Пользовательские chat sessions (можно удалять все; первая сессия больше не закреплена как undeletable).
- Drag-and-drop порядок сессий сохраняется через `PATCH /api/v1/ai/sessions/reorder`.
- Поддержка history window (`AI_HISTORY_MESSAGES`).
- Ограничение контекста по символам (`AI_MAX_CONTEXT_CHARS`).

## 6. Конфигурация

- `AI_ENABLED`
- `AI_PROVIDER`
- `AI_ENDPOINT`
- `AI_API_KEY`
- `OPENAI_API_KEY` (alias для совместимости)
- `OPENAI_BASE_URL`
- `AI_MODEL`
- `AI_TIMEOUT`
- `AI_TOP_K`
- `AI_MAX_CONTEXT_CHARS`
- `AI_HISTORY_MESSAGES`
- `AI_MCP_ENABLED`
- `AI_MCP_TOOLS_ALLOWLIST`
- `AI_MCP_PER_TOOL_LIMIT`
- `AI_SYSTEM_PROMPT`
- `AI_AGENT_QUEUE_ENABLED`
- `AI_AGENT_QUEUE_POLL_INTERVAL`
- `AI_AGENT_QUEUE_BATCH_SIZE`
- `AI_AGENT_QUEUE_RUN_TIMEOUT`

Примечание:

- `AI_PROVIDER=ollama` использует удаленный `AI_ENDPOINT` (например `http://host:11434`).
- `AI_PROVIDER=openai` использует `AI_API_KEY` (или `OPENAI_API_KEY`) и OpenAI-compatible endpoint в `AI_ENDPOINT` (или fallback `OPENAI_BASE_URL`).
- Если `AI_PROVIDER` пустой или ошибочно оставлен `ollama`, но `AI_ENDPOINT` выглядит как OpenAI-compatible (`/v1` или `/chat/completions`), backend автоматически переключает клиент на OpenAI-compatible.
- `AI_MCP_ENABLED=true` включает read-only MCP-слой tenant DB context.
- `AI_MCP_TOOLS_ALLOWLIST` ограничивает набор MCP-инструментов (`open_case_statuses`, `cases_in_work`, `recent_cases`, `recent_alerts`, `dashboard_stats`).
- `AI_MCP_PER_TOOL_LIMIT` задает верхний лимит выборки для инструментов list-type.

## 7. Проверка доступности

`/api/v1/system/health` включает модуль `ai_model`:

- ping к провайдеру (`/api/tags` для Ollama, `/models` для OpenAI-compatible)
- timeout 5 секунд на модульную проверку.

## 8. Ограничения текущей реализации

- Векторный индекс не используется, поиск text-based multi_match/phrase_prefix.
- Нет отдельного policy layer для prompt redaction.
- Для слабых локальных моделей fallback может срабатывать часто; для richer ответов нужен более сильный model/provider.

## 9. Рекомендации для прод

- Ввести structured prompt templates и output validation policy.
- Добавить safety-фильтры для данных с PII/секретами.
- Включить token accounting и latency SLO dashboard.
